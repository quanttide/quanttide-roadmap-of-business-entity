# 量潮课堂产品路线图

本目录概括量潮课堂（qtclass）的产品方向；架构与专项细节另立文件。

## 核心判断：公司造容器，基地定内容

产品交付的是容器——引擎、契约、留痕；规则本身（准入门槛、评审标准、代金券规则、旅程流程）由实训基地治理决定，产品只提供修改能力与记录。

判断来自标准倒挂：9-21 起基地自定准入门槛、公司政策跟随，基地也已能自建协作流与规章（`quanttide-training`）。产品若把流程与标准写进版本里，等于用一次发版收回一次已经下放的定义权。

由此三条约束：

- 可配置项（门槛参数、问卷题目、评审结论枚举、代金券规则）由基地代表大会决议修改，不走产品发版
- 规则变更留痕入档案（章程、账本）
- 产品不假设自己是基地唯一的流程载体——支持流程定义外置，或对接基地自建的仓库

> 依据：`data/insight/qtclass/institution-generation-path.md`（第二形态·标准倒挂）

## 架构

```text
Studio (Flutter 0.2.0)                     Provider (Go)
┌─────────────────────────┐               ┌──────────────────────────┐
│ 课程系统（现有，不动）      │               │ course：课程数据（现有）     │
│  首页/列表/播放/立项       │               │ learn：学习云代理（现有）    │
│─────────────────────────│               │──────────────────────────│
│ 实训系统（新增）           │───API───▶     │ 旅程状态机 + 持久化（新增）  │
│  旅程时间线 + 节点动作面板  │               │                            │
└─────────────────────────┘               └──────────────────────────┘
```

- 状态迁移全部是系统内事件：每个迁移是一个接口，服务端守卫
- 状态机即数据：状态表即流程定义，改流程改表，界面自动跟随——这是内容由基地自定的技术底座
- 学员身份绑定 studio 登录账号，姓名仅作显示

## 主线：studio 0.2.0

studio 现有课程系统承载内容学习（浏览课程、播放、进度、立项）；实训旅程（报名、问卷、领任务、交付、评审、入册）已在实验室工作台完成河床参考实现，免费学员资格获取流程与付费培养流程已在手册定型。0.2.0 把学习系统作为独立子系统与课程系统并列，学员端形成课程与实训双入口。

Studio 端：

- 顶层导航并列：课程（现有全部不动）、学习（新增），两系统互不侵入
- 新增学习报名页（旅程时间线加当前节点动作面板，平移实验室工作台的信息架构）、问卷页、任务页、交付页
- 评审状态在旅程面板只读展示（通过、打回附原因）；评审录入（初审、终审）属学习云

## 洞察驱动的模型要求

容器要装得下这几样，否则真实业务进不来。

- 任务来源含订单：任务可带订单来源（公司或盟友的真实需求拆成入门题，再分派成员），让课程表能跟着合同走
- 出口接订单：旅程出口（0 级、入职）与能否独立接单挂钩
- 交付前测试：交付与评审之间设跨环境测试环节，生产级判定权在真实用户与环境手里
- 意愿显性化：报名与问卷是周期性意愿确认，不是投递一次
- 成果归因：任务与交付带动作到效果的归因链，让运营、商务这类看不见的岗位获得度量衡

## 契约先行

先固化契约（旅程状态 schema、门槛配置 schema、workspace 与 task 与 workflow），再让 AI 生成 UI 与接口。河床参考实现要提炼为规格，否则课程系统、实训系统、Provider 各端会各自漂移。
