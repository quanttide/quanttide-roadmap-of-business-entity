# 先集中，后分化，再连接

功能堆叠是组织演化的必经阶段，不是设计失误。一个容器先吸收所有功能，领域分化后再把功能迁出，最终只保留交叉编排。

## 三个阶段

- **集中期**：领域信息不足，无法建立分化的容器。功能堆在最近的入口，用广度试探深度，堆功能是建模前的占位
- **分化期**：领域形成自己的容器（平台、仓库、档案），功能开始迁出
- **连接期**：中心容器只保留跨领域的编排，即交叉，不做各领域的事，只做领域之间的事。平台承载的是并行战略的编排，不是功能堆叠

## 为什么先堆功能

早期没有分化的信息，就没有分化的容器。各领域都还在摸索，中心入口是数据唯一能落下的地方。每个领域先放一个薄功能试试水，看哪个值得深入。这是探索的代偿，不是贪多。

## 为什么停止堆功能

分化完成后，堆功能的成本曲线越过收益曲线：

- 领域有了自己的容器，继续堆就是重复建设
- 命令数量过阈值后，维护成本与知识分散开始吃掉收益
- 核心问题从「什么都能做」变成「做什么才是治理」，功能碎片淹没思想表达

停止堆功能不是能力不足，是数据有地方去了。

## 切换判据

- 领域是否已经有了自己的容器
- 堆功能的边际成本是否开始超过收益

两条都满足，就该切换阶段。这个判据适用于其他仓库的演进，也解释了意图实现差距的来源：实现停留在集中期，意图已经走到连接期。

## 实现位置

qtadmin 已走完分化主路径：业务域（qtclass、qtcloud、qtconsult、qtdata、qtrecurit）全部从 CLI 移除并归位各平台仓库，share 迁至 devops 实验室，CLI 收敛为五个职能域命令。

三支柱只覆盖一角：asset 已落地（archive、status、quality），delib 与 strategy 仍零实现。连接期的目标——中心容器只保留跨领域编排——尚未达到，治理可视化空白（Studio 无治理页面）。

连接期要补齐的交叉编排：产教融合（把各平台工作整合成学习进度）；strategy 载体（战略第二大脑：事实审计加反事实推演，假设库结构化，从日志蛛丝马迹发掘）。

## 基础能力

连接期的基础设施：让各支柱可以生长，让领域知识有地方安放。

### 职能域下沉领域层

- human、asset、connect 的规则和数据定义沉淀到领域档案与规格层，CLI 只保留执行入口
- 当前仍有领域知识直接编码在命令中（human 的 position/config、asset 的 git_utils 等）
- 遵循「显性化即可转移」：经验显性化到档案与规格，组织才能接管

### 数据契约

- 恢复 Provider 演进：字段与档案同源（criteria.json 同源模式），保证评估字段与信任字段同构契约
- Studio 与 CLI 从本地文件直读升级为服务端承载

### 封装边界

- AI 产出必须可落地：落不了地的产出是债务，不进入封装
- 知识承载以状态区分（settled / evolving / draft）：模糊是演进中的合法承载状态，不强制澄清

### 演进方向

- 优惠券和代金券是未来代币的前身：用交付和知识资产作为底牌发债
- 体系跑通的前提是产能突破瓶颈——不靠堆人，靠系统

## 边界

- 分化未完成时强行拆分，功能无处安放
- 交叉点不是剩余物，是中心容器的终极形态，且不靠人为强推，分化充分后自然涌现
- 同一规律作用于人：身兼两职是人的集中期，单点故障源于职能重叠，分化应把职能分散

## 迁移例证

同样的形状：单体应用、微服务、网关；小公司全员全能、部门化、总部战略协调；城市中心集市、专业化街区、交通枢纽。
