# 量潮云产品研发路线图

统一目标：帮助人类消除人机协作摩擦的第二大脑。

## 病根：流程破碎（河床）

2026-09-07 日记「河床」（`data/journal/qtcloud/2026-09-07.md`）的诊断：

> 一个学员的旅程横跨约十个系统，每个衔接点都是「人肉路由器」；状态机的迁移全靠人肉对账伪造。之前一切自动化收效甚微，是因为在给一条断河修闸门；真正该做的是把河修连续。

量潮自己的流程就是证据：每个环节内部早已自动化，真正吃人的是**环节之间的衔接**——靠人把状态搬来搬去。平台要解决的根本问题是这个：不是缺功能，是河不连续。

## 定位

量潮云是一个工作平台（Workbench）：承载工作的软件系统。第一职责是筑河床——承载连续旅程，状态机由规则自动推进，人只在闸门（验收）出现。形态对标 CoWork/WorkBuddy，底层是自己的云。

## 概念基座

通用语言由工程标准定义（`quanttide-specification-of-business-entity/work/index.md`）：

| 概念 | 定义 |
|:-----|:-----|
| 工作平台 Workbench | 承载工作的软件系统 |
| 工作空间 Workspace | 围绕一个上下文组织工作的容器，空间之间相互独立 |
| 任务 Task | 工作的最小单元，有执行者与完成判定 |
| 工作流 Workflow | 任务按依赖编排成有向无环图（DAG） |

连续性由状态规则保证：任务状态由规则推进（上游验收通过即就绪、云交付即待验收、入档须闸门），不靠人肉对账。概念直接落为契约（workspace / task / workflow 最小 schema），各端读契约不读文档。执行者与交付物是下一组入册概念，随协作目录落地补充。

不再分期演化：一次建成一条连续的河，不是断片的堆。

## 验收场景

范围以场景为限，当前两场：

1. **最糙的连续**（河床原话）：报名 → 问卷 → 领任务，站内三步连着走完；旧系统（邮箱、飞书表单、Bitable、群）逐段退场降级为异常通道与镜像。
2. **招聘政策接力**（2026-08-05 已跑通的模块接力，`data/journal/qtcloud/2026-08-05.md`）：任务输入 → 拆解 → 多模块接力（沟通 → 知识工程 → 人事）→ 交付草案 → 验收入档。

## 交付顺序

内部依赖序，全部并行开工、按此合入：

1. 概念契约：workspace / task / workflow schema（含状态推进规则）
2. 状态机引擎：任务状态由规则推进，人肉衔接点清零
3. 协作目录：执行者注册与事件契约模型
4. Studio 工作台：先承载最糙的三步旅程，再承载政策接力
5. 执行端点：数据云、议事云接入任务协议

## 版本

一次性发布 studio/v1.0.0：CoWork 完整形态 + 两场验收闭环。门户由 site/v0.1.x 承载，已就位。

## 外围（随业务演进，不阻塞交付）

- 专家资产化：各云沉淀 SOP 与知识库，企业专属专家，按量交付
- 项目空间：多 Workspace 协作（外层 DAG）、流程沉淀复用——待空间模型内部验证后解禁
- 云业务扩张、双引擎（增长与管理）、招聘投递进社区、客服云
- 经验显性化：把生产验证中积累的经验变成显性平台流程（2026-09-08）

## 原则

- **连续优先于完备**：先把河修连续，再修断片内部
- **先定河床，旧系统逐段退场**
- 从做对的系统到做活的系统
- 概念即契约：先定义通用语言，再写实现代码
- 内部先用：量潮自己的工作流优先，集成靠任务协议不靠代码依赖
- 范围以验收场景为限：场景之外的愿望进外围清单，不进交付
- 云体系的精密是系统级别的精密，不是单个功能的精密
- 用外部视角检验：开源结构加不断发布招聘，把项目融入其中
- 增长飞轮精密复杂，一言不合就可能会崩溃
