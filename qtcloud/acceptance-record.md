# 验收记录：执行云 0.2 的第一块

## 要解决什么问题

过去一个月发布了三十多个 MVP，现在要把有用的拼到一起。拼装的困难是：东西太多，人不清楚每个东西是谁做的、质量如何、被谁认可过——理解成本没有数据。

解法：**把「验收」这件事记录下来**。谁交的、谁看的、结论是什么、改了几次。一张表。

## 表长什么样

以代表评审课题为例：

| 字段 | 例子 |
|------|------|
| 谁交付 | 学员的课题《流程状态数据底座》 |
| 谁验收 | 代表 |
| 结论 | 退回修改 |
| 修改次数 | 1 |
| 归因链接 | deliberation 仓库的评审议题 |

结论只有四种：直接采纳 / 采纳但改了 / 退回修改 / 待定。其中「采纳但改了」信息量最大——既说明方向对，又说明还差功夫。

## 为什么它排第一

四个已经在发生的事情，都缺这张表：

1. **评审正在发生**——代表评课题已经通过过、退回过，但记录散在群聊里，评完就丢
2. **获客可以算账**——链接 → 入群 → 领任务 → 转化的链路已经真实发生，补上记录就是 20% 销售提成的分成依据，也是运营岗的成果凭证
3. **AI 需要信誉**——AI 只有建议权，建议被采纳或修改的记录，就是 AI 的票数
4. **执行云 0.2 需要它**——意图文档里 0.1→0.2 的质变点就是验收机制

先给谁用（按顺序）：

1. 代表评审——正在发生，直接把群聊里的评审换成这张表
2. 获客台账——已发生的转化链补上记录
3. AI 工作记录——AI 每天提交 journal/insight，记下采纳还是改了

## 怎么知道做错了

一个月后：如果评审的人嫌麻烦不填，或者填了没人看，说明表设计错了。

## 这次不做什么

- 去平台化卖产品——还没有真实客户成交，等盟友第一批线下对接的结果
- 两个主体的成人礼——等它自然发生，不排期
- 课堂 vs 招聘的效率对比——需要这张表先积累几个月数据
