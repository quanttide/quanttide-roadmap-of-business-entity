# 验收记录：执行云 0.2 的第一块

> 问题：拼装期的认知负担不可度量——三十余个 MVP 并行后，理解成本没有数据。承载：建议/验收记录数据模型，先在内部工作流运行，再产品化为执行云功能。

## 预测依据（为什么这一块排第一）

四个来源收敛，且均已被现实部分验证：

- 意图侧：`data/insight/qtcloud/qtcloud.md` 矛盾一——0.1→0.2 的质变点是验收机制成为一等公民，路径已定（招聘政策案例端到端）
- 治理侧：代表评审双样本已发生（9-03 通过、9-04 退回修改）——验收流在真实治理中跑通过两轮
- 制度侧：AI 只有建议权，「建议被采纳的频率与质量就是 AI 的票数」需要记录承载（`data/insight/intro/power-capped-by-responsibility.md`、`data/insight/qtcloud/qtcloud-agent.md`）
- 运营侧：运营/商务岗位的成果需要归因机制才能被看见（`data/insight/qtclass/outcome-attribution.md`）

## 数据模型（最小版）

```
谁交付 → 谁验收 → 结论（采纳/采纳并修正/退回/待定）→ 修改次数 → 归因链接
```

与 insight 仓库的 SuggestionRecord 设计（`qtcloud-agent.md`）同构；「采纳并修正」是最有信息量的状态——同时说明建议有价值（值得采纳）和有缺陷（需要人修正）。

## 推广顺序

1. **评审流**：代表课题评审记录结构化——正在发生的治理动作，直接换载体
2. **获客归因流**：链接 → 入群 → 领任务 → 转化——已发生的转化链补台账，同时是 20% 销售提成的分成依据
3. **内部工作流**：journal/insight 提交的采纳记录——AI 信誉的第一批数据点

## 证伪条件

若代表评审与内部工作流都填不出结构化记录，说明字段设计错误——一个月内可见分晓。

## 非目标

- 去平台化市场侧：零成交证据，等盟友第一批线下对接反馈
- 两个主体碰撞的成人礼：真实但不可排期，进观察清单
- 基准线测量（课堂 vs 招聘效率）：依赖本记录的数据积累，顺序在后
