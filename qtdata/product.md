# 量潮数据产品迭代路线

核心问题：职能分解是为了内部执行方便（不同职能分别去做），但客户看到的是一个完整的业务流程。业务域要做的是**从职能域提取相关内容，重组成一个完整的子领域，然后直接用这些概念去表达**。

## 职能分解与客户视角

多个职能之间有重合的地方——比如数据处理流程和项目排期。把这些拆开，是为了方便不同职能分别去做。但对客户来讲，他需要看到的是：**项目的 5 个阶段，每个阶段有某一个角色在做某一块的事情，按明确的顺序进行。**

职能分解是内部的事，客户视角是业务域的事。

## 业务域的定义与重组

把一整套东西定义为一个「业务域」：

1. **从职能域提取**：数据分析、商务、项目管理——各职能域里跟这个业务相关的部分
2. **重组成一个子领域**：「量潮数据」——不是职能的拼装，是一个完整的业务概念体系
3. **直接用业务域的概念表达**：客户看到的是「量潮数据」的 5 个阶段、每个阶段谁做什么、按什么顺序——不是「数据处理模块 + 商务模块 + 项目模块」

## 具体整合点

### 逐阶段整合

**调研**（商务经理接需求 + 数据工程师评估可行性）：报价（成本法/市场法）和数据需求分析合并为「需求评估」——报价不是独立动作，是调研阶段的输出；项目立项是调研结束的标志。

**谈判**（商务经理签合同 + 数据工程师出方案）：合同签订是谈判阶段的交付物；处理流程设计（蓝图 6 步）是谈判阶段给客户看的「方案」，不是「数据域的东西」；排期和方案是同一件事的两面（做什么 + 什么时候）。

**实施**（数据工程师执行 + 商务经理跟进）：处理流程执行和异常预案标注影响哪个交付物；交付时间线是实施阶段的客户视图；过程资产（矩阵格）是实施阶段的中间产物，不是「资产域的东西」。

**验收**（客户验收 + 商务经理确认）：交付物清单是验收的对象；验收标准是商务域定的，但客户在验收阶段才看到；项目域的「验收节点」和客户说的「验收」是同一件事。

**复盘**（双方复盘 + 归档）：资产归档是复盘的产出；结款是复盘阶段的商务动作；复盘报告不是「项目域的报告」，是业务域的收尾。

### 横切整合点

| 现状 | 整合方向 |
|---|---|
| 矩阵（3 维×5 阶段）在资产页，商务步骤条又用同一组列 | 统一为「阶段进度条」——一条跨五页共享，不再两个地方各画一遍 |
| 交付物出现在总览明细 + 资产矩阵格两处 | 统一为「交付物」——只在验收阶段出现一次 |
| 蓝图六步 + 时间线六阶段 + 矩阵五阶段 = 三套分解 | 统一为「5 阶段」——客户只看一套，职能域的细分是内部的事 |
| 工作档案按职能组织（数据分析/商务/项目各自一摊） | 按「量潮数据」业务域组织——每个阶段一个文档，里面写清谁做什么 |
| 宣传册/工作教程/工作手册各自独立 | 都按「量潮数据」的 5 阶段组织——客户视角统一，新人培训也统一 |

## v0.2.0 — 界面重组（当前）

把业务域的表达落到客户端界面。不加功能、不改数据层，只解决一个问题：让客户打开看板能回答「现在在哪、有没有风险、下一步做什么」。

- **五页重组**：总览→决策页（状态＋风险＋下一步）、数据→方案页（流程＋风险标注影响）、项目→排期页（时间线＋里程碑）、商务→纸面页（报价/合同/交付/结款）、资产→证据页（交付物＋过程资产）
- **砍两处重复**：交付物明细移资产页；商务管理阶段步骤条删除
- **拆大卡**：项目卡→三张小卡；蓝图卡→两张卡（流程/风险）
- **加反馈入口**：总览页顶部「联系项目经理」＋每页底部轻量入口
- **跨页主线**：五页共享阶段进度条（调研→谈判→实施→验收→复盘）
